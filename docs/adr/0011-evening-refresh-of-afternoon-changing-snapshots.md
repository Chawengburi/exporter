# snapshot ของ HotelTime ถ่ายซ้ำรอบ 18:00 (ขยาย ADR-0008)

2026-11-13 · `ht_gold_in_house_guest` ของวันนี้ขาดแขกห้อง 505 (reservation 603444268) — เช็คอิน 14:15 แต่ snapshot `in-house-guests` ถ่ายตอน 12:07 ครั้งเดียว
และรอบเก็บตก 15:00/18:00 ใช้เวลา `0s` เพราะตัววางแผนถือว่า snapshot ของวันนี้ "สำเร็จแล้ว" (สถานะเป็นรายวัน) · เวลา check-in คือ 14:00 เที่ยงจึงเป็นช่วงที่ข้อมูล
in-house นิ่งน้อยที่สุด

**ADR-0008 ไม่ได้ห้ามถ่ายซ้ำ** (บอกไว้แล้วว่า snapshot ทุกครั้งเป็นฉบับใหม่ "รองรับการดึงถี่ขึ้นภายในวันในอนาคตได้โดยไม่ต้องเปลี่ยนแนวคิด") — ข้อจำกัดอยู่ที่ตัววางแผน
(`due` ตัดทุกอย่างที่ `isDone` ของวันนั้น) และ docstring ของ `runDaily` · ADR-0003 (`dailyOnly` ไม่ back-fill) และ ADR-0009 (เติมวันที่ขาดของรายงานตามวัน) ไม่เกี่ยว
ใช้ได้ตามเดิม

**ทางที่เลือก:** snapshot **ทุกใบของ HotelTime** ตั้ง `refreshAtHour` = `EVENING_REFRESH_HOUR` (18) ผ่าน `toPlanned` จุดเดียว — ตั้งแต่ชั่วโมงนั้นของวัน ถ้า snapshot ปกติ
ของวันนี้สำเร็จแล้ว ตัววางแผนใส่ใบนั้นใน `refreshes` ถ่ายซ้ำอีกหนึ่งครั้ง · รายงานตามวัน (ADR-0008) และ FoodStory ไม่ตั้ง = เดิมทุกประการ ·
(เดิมตัดสินไว้ 4 ใบ: in-house-guests, rooms-status-overview, arrivals, departures — เปลี่ยนเป็นทุกใบเพราะต้นทุนต่ำกว่าที่ประเมิน และหลายใบเปลี่ยนหลังเที่ยง
เช่น สถานะห้อง ยอดค้าง ยอดสะสมของวัน โดยไม่ต้องไล่ตัดสินทีละใบว่าฝั่ง gold ใช้ใบไหน)

- **บันทึกผลด้วย id แยก `<รายงาน>@refresh`** (แบบเดียวกับ `@period-close`) ไม่ใช้ id เดิม — `_run.json` เก็บได้หนึ่งสถานะและหนึ่งชุด `files[]` ต่อ id ต่อโฟลเดอร์
  ถ้าใช้ id เดียวกัน รอบเย็นจะแทนไฟล์รอบเที่ยง แล้วถ้าไฟล์เที่ยงยังค้างอัปโหลด ขาอัปโหลดหา `as_of` ของมันไม่เจอ (`findOutcomeForFile`) และปฏิเสธถาวร
- ไฟล์ชื่อตามเวลาที่ถ่ายเหมือนเดิม จึงไม่ทับกัน · ถ่ายซ้ำเฉพาะเมื่อ snapshot ปกติสำเร็จแล้ว (ถ้ายังไม่สำเร็จ รอบนั้นถ่ายใหม่อยู่แล้ว ไม่ถ่ายสองใบ) · ล้ม = ลองใหม่ในรอบถัดไปของวันเดียวกัน (รอบ 18:00 เป็นรอบสุดท้าย)
- `exporter status` / Discord: "snapshot N/N" ยังนับต่อรายงาน (ไม่เบิ้ล) · ถ่ายซ้ำล้ม **ไม่ใช่ปัญหา** (ตัดสินใจ 2026-11-13 ตามคำแนะนำของอีกทีม — รอบเที่ยงยังใช้ได้) บอกในสรุปเป็น
  "ถ่ายซ้ำรอบเย็นล้ม N (ชื่อ)" / `evening re-take failed: …` ไม่มีข้อความแจ้งเตือน · ถ่ายซ้ำที่ "ยังไม่ได้รัน" ไม่ถูกบอก (ให้ฝั่ง consumer ตรวจ `as_of` ล่าสุดเอง)
- ขาอัปโหลด: `RawFileEntry.report` ยังเป็น id รายงานเดิม (document_type / `as_of` guard ใช้ (รายงาน, ช่วง) เดิม) · ถ้าไฟล์รอบเที่ยงยังค้างอัปโหลดตอนที่ไฟล์รอบเย็นขึ้นไปก่อน ไฟล์เที่ยงจะถูกกัน
  `as_of` ย้อนหลัง (blocked-as-of) — ตั้งใจ: ฉบับเย็นใหม่กว่าและครอบทับฉบับเที่ยงอยู่แล้ว · snapshot รอบเย็นที่ "ว่าง" ไม่ตั้ง backlog ว่างที่ยังไม่ประกาศ (ไม่มีทางประกาศได้ จะค้างทั้งวัน)
- ฝั่ง consumer (`hoteltime-schema`): `011_in_house_guest.sql` เลือกไฟล์ `as_of` ล่าสุดเอง · `008_occupancy_snapshot.sql` เก็บทุกรอบเป็นประวัติ · pipeline 19:00 อยู่หลังรอบ 18:00
  — ยังไม่ได้ทดสอบกับไฟล์ 2 รอบต่อวันจริง

**ทางที่ไม่เลือก:** เลือกถ่ายซ้ำเฉพาะบางใบ (ต้องไล่ดูว่า gold ใช้ใบไหน และพลาดใบที่เปลี่ยนหลังเที่ยงโดยไม่รู้ตัว) · ทำสถานะต่อรอบ (slot) ให้ทุก snapshot (ใหญ่เกินจำเป็น) ·
เพิ่ม cron เฉพาะ (Windmill job ใหม่ — ความจริงอยู่สองที่ ดู ADR-0009)

**ผลที่ตามมา:** รอบ 18:00 ของ HotelTime ไม่ใช่ `0s` อีกต่อไป (เพิ่มราว 3–4 นาที — snapshot ชุดเต็ม ≈ 177 วินาที ตาม ADR-0009 กรณีหนักสุดรวมเติมวันที่ขาดราว 10 นาที เท่ารอบเที่ยง · ยังไม่ได้วัดจริง ต้องดู timeout 15 นาที และคิวร่วมกับ FoodStory หลัง deploy) · ไฟล์ snapshot ต่อวันเพิ่มเป็นสองเท่า · แขกที่เช็คอินหลัง 18:00
ยังไม่เข้า snapshot ก่อน pipeline 19:00 — ค้างรอคำตอบ FO (เที่ยวบิน/เรือเที่ยวสุดท้าย เวลา night audit) ว่าต้องเพิ่มรอบดึกไหม
