# 02 · ข้อจำกัดของ HotelTime ที่บังคับดีไซน์

> 🔴 **อ่านใบนี้ก่อนแก้โค้ดใด ๆ** ทุกข้อในนี้วัดมาจากของจริงเมื่อ 2026-09-08
> หลักฐานเต็มอยู่ใน [`../recon/NOTES.md`](../recon/NOTES.md)
>
> ข้อจำกัดพวกนี้ไม่มีอันไหนที่ HotelTime บอกเราตรง ๆ — ทุกอันพังแบบ **เงียบ** ทั้งนั้น
> คือได้ไฟล์ที่หน้าตาปกติแต่ข้อมูลผิด นั่นคือเหตุผลที่ต้องเขียนไว้ให้ครบ

## 1. เพดาน 2000 แถว (เฉพาะ `ReservationListMaster`)

สั่ง `01/01/2024 → 08/09/2026` ได้ไฟล์ที่มีข้อมูลแค่ `23/05/2024 → 15/01/2025` **2000 แถวพอดี**
ไม่มี error ไม่มีคำเตือน ไม่มีตัวแบ่งหน้าให้กดต่อ

⚠️ **ตัวเลขสรุปท้ายหน้าเว็บกันเรื่องนี้ไม่ได้** เพราะถูกคำนวณ *หลัง* โดนตัดแล้ว มันจึงรายงาน
2000 ตรงกับไฟล์เสมอแม้ข้อมูลหายครึ่งหนึ่ง — ด่านที่จับได้จริงคือการเทียบ *ช่วงวันที่ในไฟล์*
กับช่วงที่สั่ง

**การตัดเรียงตาม created date จากเก่าไปใหม่** จึงเดาได้ ไม่ใช่สุ่ม → การซอยช่วงเป็นก้อนย่อยแก้ได้ทั้งหมด

**ตัดสินใจ: ซอยรายเดือน** (ไม่ใช่รายไตรมาส)

| ขนาดก้อน | แถวสูงสุดที่วัดได้ | headroom |
|---|---|---|
| ครึ่งปี | 🔴 ชนเพดาน | — |
| ไตรมาส | 1,353 (2025 Q1) | 32% |
| **เดือน** | **662 (2025-01)** | **3 เท่า** |

ไตรมาสใช้ได้ *วันนี้* แต่ถ้าโรงแรมโตขึ้นจะชนโดยไม่มีใครรู้ · บวกตัวกันพลาดแบบปรับตัวเอง:
ก้อนไหนได้ 2000 พอดีให้ถือว่าชนเพดาน แล้วผ่าครึ่งดึงใหม่จนต่ำกว่า

## 2. ช่วงวันที่ถูกกรอกมาให้ล่วงหน้า (ทุกหน้า)

| หน้า | ช่องที่ถูกกรอกมาแล้ว | ค่า default |
|---|---|---|
| `ReservationListMaster.aspx` | `calArrival` — Arrival date range | วันนี้ → **อีก 1 ปี** |
| `reports/ResListRateCode.aspx` | `cal` — Period | วันนี้ → พรุ่งนี้ |
| `ResDeleteList.aspx` | `drStay` — Stay date range | วันนี้ → อีก 7 วัน |

ถ้ากรอกแต่ created date แล้วปล่อยช่องพวกนี้ไว้ จะได้ **intersection ที่ไม่มีใครสั่ง**

**พิสูจน์แล้วว่าเกิดจริง:** ทดสอบ created `01–07/09/2026` ได้ไฟล์ที่มี Arrival ถึง `16/08/2027`
ซึ่งแถว arrival `01–06/09/2026` จะหายทั้งหมดถ้าปล่อยค่า default ไว้

**ตัดสินใจ:** `applyFilters()` ของทุกรายงาน **ต้องจัดการช่องเหล่านี้อย่างชัดเจน** ไม่ใช่แค่
กรอกช่องที่ต้องการ · วิธีจัดการต่างกันตามข้อถัดไป

## 3. `Period:` ของใบ RateCode เป็นฟิลด์บังคับ — ห้ามล้าง

ล้างแล้วหน้า re-render พร้อมป้าย `* mandatory item` โดยไม่มี error ที่มองเห็นชัด และ
🔴 **ลิงก์ export ของหน้านั้นอยู่ตลอดเวลา** (อยู่ในเมนู "Other operations" ไม่ได้โผล่ตามผลลัพธ์)
การกด export ตอนนั้นจึงได้ไฟล์ที่ไม่ตรงกับที่สั่ง

**ตัดสินใจ:** ตั้ง `Period` ให้กว้างจนไม่กรองอะไรแทน — `01/01/2020 → 31/12/2030` ·
และเพิ่มด่าน `assertFormAccepted()` ที่เช็คคำว่า `mandatory item` **ก่อน** กด export ทุกครั้ง

## 4. ผลลัพธ์ว่าง = ไม่มีไฟล์ส่งมาเลย

ค้นเดือนที่ไม่มีข้อมูล (เช่น ม.ค. 2024) แล้วกด export → **เงียบสนิท 45 วินาที ไม่มีไฟล์**
ทั้งที่ลิงก์ export ยังอยู่

**ตัดสินใจ:** `Report.hasResults()` ต้องถูกเรียก **ก่อน** กด export เสมอ · สัญญาณต่างกันทุกใบ
จึงให้แต่ละรายงานตอบเอง (ใบแรกดูแถวสรุป · RateCode ดูว่ามีตาราง `#pc_dtgData` ไหม ·
Cancelled ดูจำนวนแถวใน `#pc_dtgItems`)

ถ้าไม่มีด่านนี้ การดึงย้อนหลังจะเสียเวลาไปกับการรอ timeout ทุกเดือนที่ว่าง (search มี 4 เดือน,
cancelled มี 27 เดือน)

## 5. ไฟล์ xlsx ที่ได้มีสองกับดัก

**5.1 `openpyxl` และตัวอ่านที่ parse stylesheet อ่านไม่ได้** — HotelTime เขียน `xl/styles.xml`
ผิดสเปก (`vertical` alignment ค่าไม่อยู่ใน enum ของ OOXML)
→ `ValueError: Unable to read workbook: could not read stylesheet`

**ตัดสินใจ:** เขียนตัวอ่านเองใน `core/xlsx.ts` ที่อ่านเฉพาะ `sharedStrings.xml` + worksheet
และ **ไม่แตะ `styles.xml` เลย**

**5.2 เซลล์ว่างถูกตัดออกจาก XML** — header 22 ช่องแต่แถวข้อมูลมี ~15 ช่อง การไล่อ่านตามลำดับ
ที่เจอจะทำให้ค่าเลื่อนคอลัมน์ทั้งแถวโดยไม่มีอะไรฟ้อง

**ตัดสินใจ:** อ่านตำแหน่งคอลัมน์จาก attribute `r` (เช่น `r="B2"`) เสมอ

**5.3 วันที่มาสองรูปแบบ** — ใบแรกเป็นข้อความ `01/09/2026` · ใบ RateCode เป็น **Excel serial**
`45658` · ใบ Cancelled เป็น serial **ที่มีเศษเวลา** `46142.757265625`

**ตัดสินใจ:** `parseCellDate()` รองรับทั้งสองแบบ และ `excelSerialToDate()` ใช้ `Math.floor`
ไม่ใช่ `Math.round` (ดู spec 04 — เคยเขียน round แล้วชั้นตรวจจับได้)

## 6. timezone เหลื่อม 7 ชั่วโมงในคอลัมน์ `Cancelled`

ค่าที่ export เป็นเวลาท้องถิ่น (UTC+7) แต่ตัวกรองตัดขอบด้วย UTC · ช่วง `01/05–31/05` จึงคืนค่า
ถึง `01/06/2026 01:40` เวลาไทยได้โดยชอบธรรม (= `31/05 18:40 UTC` ซึ่งยังอยู่ในช่วง)

**ไม่ทำให้ข้อมูลซ้ำหรือขาด** เพราะตัวกรองฝั่ง server เป็นตัวตัดสินว่าแถวไหนอยู่ก้อนไหน
แต่ละแถวจึงอยู่ก้อนเดียวเสมอ

**ตัดสินใจ:** `boundaryToleranceDays: 1` เฉพาะรายงานนี้ · อีกสองใบเป็น `0`
🔴 **อย่าตั้งค่านี้เพื่อ "ให้ผ่าน"** — ด่านนี้คือด่านเดียวที่จับได้ว่า filter ไม่ทำงาน

## 7. อันตราย — ปุ่มที่แก้ไขข้อมูลอยู่ในหน้าผลลัพธ์

`ResDeleteList.aspx` หลังกด Search มีปุ่ม **`Reinstate room` 21 ปุ่ม**
(`ctl00$pc$dtgItems$ctlNN$ctl06`) ซึ่ง **คืนสถานะห้องที่ยกเลิกไปแล้ว = เขียนข้อมูลจริง**

**กฎบังคับ:** โค้ดคลิกได้เฉพาะปุ่ม Search ที่ระบุชื่อ control ตรง ๆ กับลิงก์ `Export: MS Excel`
เท่านั้น · 🔴 **ห้ามใช้ locator แบบกวาดแล้ว `.first()` / `.nth()` เด็ดขาด** ·
`uniqueByRole()` ช่วยได้เพราะจะล้มทันทีถ้าเจอหลายชิ้น
