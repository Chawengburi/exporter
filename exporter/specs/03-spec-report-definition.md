# 03 · การนิยามรายงาน

## ตัดสินใจ: หนึ่งไฟล์ TypeScript ต่อหนึ่งรายงาน ไม่ใช่ JSON config

เจ้าของบอกตั้งแต่ต้นว่า "แต่ละไฟล์มี filter ที่ค่อนข้างเฉพาะตัว" · พอสำรวจจริงพบว่ามันลึกกว่านั้น
สามรายงานที่ดูเหมือนกันจากเมนู **ต่างกันทุกมิติที่สำคัญ** (ดูตารางท้าย spec 02)

ถ้าใช้ JSON config เราจะต้องใส่ฟิลด์แบบ `"clearDateRanges": [...]`, `"widenDateRanges": {...}`,
`"emptyDetector": {"kind": "grid", "selector": "#pc_dtgData", "minRows": 1}` แล้วเขียน
interpreter มาอ่านมัน — **นั่นคือการประดิษฐ์ภาษาโปรแกรมครึ่งใบที่ไม่มี type checking
ไม่มี autocomplete และ debug ยากกว่าเดิม**

TypeScript ให้ทั้งอิสระ (แต่ละใบเขียนตรรกะของตัวเองได้) และความสม่ำเสมอ (ทุกใบ implement
interface เดียวกัน คอมไพเลอร์บังคับให้ครบ)

## สัญญา `Report`

อยู่ที่ [`../src/reports/_types.ts`](../src/reports/_types.ts) · ทุกฟิลด์มีเหตุผลกำกับในโค้ด

| ฟิลด์ | หน้าที่ | กับดักที่มันแก้ |
|---|---|---|
| `path` | path ใต้ `/pms/` | เมนูเป็น `<a href>` จริง จึง `goto()` ตรงได้ |
| `chunk` | `monthly` หรือ `whole` + **เหตุผลเป็นข้อความ** | กันคนมา "ปรับให้เร็วขึ้น" แล้วข้อมูลหาย |
| `hasRowCap` | ใบนี้ชนเพดาน 2000 ได้ไหม | เปิดด่านผ่าครึ่งอัตโนมัติ |
| `boundaryToleranceDays` | ค่าเผื่อขอบช่วงวันที่ | timezone เหลื่อม (spec 02 ข้อ 6) |
| `dateColumn` | คอลัมน์ที่ใช้ยืนยันว่า filter ทำงาน | ด่านสำคัญที่สุดของชั้นตรวจ |
| `dateColumns` | คอลัมน์วันที่ทั้งหมด | แปลง Excel serial ตอนเขียน CSV |
| `expectedColumns` | หัวตารางที่คาดหวัง | รายงานถูกแก้ที่ฝั่ง HotelTime แล้วเรารู้ทันที |
| `searchButton` | ชื่อ control ของปุ่ม Search | ระบุตรง ๆ ไม่ให้ไปโดนปุ่มอันตราย |
| `applyFilters()` | ตั้ง filter **และจัดการช่วงวันที่ default** | spec 02 ข้อ 2 และ 3 |
| `hasResults()` | ค้นแล้วเจอไหม | spec 02 ข้อ 4 — ผลว่างไม่ส่งไฟล์ |
| `expectedRowCount()` | จำนวนแถวที่หน้าเว็บบอก คืน `null` ถ้าเชื่อไม่ได้ | เทียบกับไฟล์ที่ได้ |

### `chunk.reason` เป็นข้อความบังคับ ไม่ใช่ฟิลด์ประดับ

```ts
chunk: {
  kind: 'monthly',
  reason: 'HotelTime ตัดผลลัพธ์ที่ 2000 แถวเงียบ ๆ — ปี 2025 และ 2026 ชนเพดานทั้งคู่ …',
}
```

เพราะการซอยรายเดือนดู "ช้าเกินจำเป็น" สำหรับคนที่ไม่รู้เรื่องเพดาน · คนถัดไปที่มาเห็นจะอยากรวม
เป็นรายปีเพื่อให้เร็วขึ้น แล้วข้อมูลจะหายเงียบ ๆ · ข้อความนี้ถูกพิมพ์ออกมาทุกครั้งที่รัน
และแสดงใน `pms-export reports` ด้วย

### `expectedRowCount()` คืน `null` ได้ และต้องคืนเมื่อเชื่อไม่ได้

มีแค่ใบ `reservations-search` ที่แถวสรุปตรงกับจำนวนแถวในไฟล์พอดี (65 = 65) ·
ใบ RateCode ให้ค่าว่าง · ใบ Cancelled นับ *reservation* ไม่ใช่ *แถว* (หน้าเว็บบอก 19 แต่ไฟล์มี 22)

🔴 **อย่าเดา** — คืน `null` แล้วให้ชั้นตรวจข้ามด่านนั้นไป ดีกว่าเทียบกับตัวเลขที่หมายถึงคนละอย่าง
แล้วได้ false alarm ทุกรอบจนคนเลิกอ่าน

## วิธีเพิ่มรายงานใหม่

1. **สำรวจก่อนเขียนโค้ด** — เปิดหน้าจริง เก็บหกข้อตามเทมเพลตใน `recon/NOTES.md`
   (เส้นทางเมนู · filter ทุกตัวและตัวไหน auto-postback · ปุ่ม export · ไฟล์มาทางไหน ·
   ใช้เวลาเท่าไหร่ · หน้าตาไฟล์) · **ห้ามเดาจากรายงานใบอื่น** — สามใบที่มีอยู่ไม่เหมือนกันเลย
2. ทดสอบขนาดช่วงที่ปลอดภัย — ลองเดือน/ไตรมาส/ปี ดูว่าชนเพดานหรือ export พังที่ขนาดไหน
3. เขียน `src/reports/<id>.ts` implement `Report`
4. ต่อท้าย `REPORTS` ใน `src/reports/index.ts`
5. รันช่วงแคบ ๆ ก่อนด้วย `--from`/`--to` แล้วดูว่าชั้นตรวจผ่าน
6. บันทึกสิ่งที่เจอลง `recon/NOTES.md`

## รายงานที่มีตอนนี้

| id | หน้า | ซอยก้อน |
|---|---|---|
| `reservations-search` | `ReservationListMaster.aspx` | รายเดือน |
| `reservations-ratecode` | `reports/ResListRateCode.aspx` | ทั้งช่วง |
| `reservations-cancelled` | `ResDeleteList.aspx` | รายเดือน |

ทั้งสามกรองด้วยวันที่สร้าง (`created date`) ตามที่เจ้าของกำหนด **ยกเว้นใบ Cancelled
ที่ไม่มีช่องนั้น** จึงใช้ *วันที่ยกเลิก* แทน — เจ้าของตัดสิน 2026-09-08 โดยให้เหตุผลว่า
วันที่ยกเลิกเป็นอดีตล้วนแก้ย้อนหลังไม่ได้ คุณสมบัติเดียวกับ created date

⚠️ **ผลที่ตามมาที่ต้องรู้:** ใบที่ *สร้าง* ปี 2023 แต่ *ยกเลิก* ปี 2024 จะติดมาด้วย —
เป็นประชากรคนละชุดกับ "สร้างตั้งแต่ 2024" อย่าเอาไปรวมกันโดยไม่คิด

## ทำไมเลือกกรองด้วย created date

เจ้าของระบุ: arrival / departure / stay มีข้อมูล **อนาคต** ปนอยู่ซึ่งยังเปลี่ยนได้ และเราจะไม่ได้
ข้อมูลครบ · ส่วน created date เป็นอดีตล้วน แก้ย้อนหลังไม่ได้ แต่ละรอบ export จึงเป็น
**append-only** และเทียบกับรอบก่อนได้จริง

ผลที่ตามมาที่ดีสำหรับอนาคต: หลังดึงย้อนหลังครบแล้ว รอบถัด ๆ ไปดึงแค่เดือนปัจจุบันก็พอ (~3 วินาที)
