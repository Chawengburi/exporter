## 3. ทางเลือกในการเอาข้อมูลออก

### ทางเลือกที่พิจารณา

| # | วิธี | ได้ผลไหม | ข้อสรุป |
|---|---|---|---|
| A | **อ่านตาราง HTML จากหน้าเว็บตรง ๆ** | ✅ ข้อมูลอยู่ใน `#pc_dtgList` ครบ | **เลือกทางนี้** |
| B | `Print version` → พิมพ์เป็น PDF | ได้ไฟล์ แต่เสียโครงสร้างตาราง | ❌ ต้องมา parse PDF ต่อ แย่กว่าอ่าน DOM |

| D | **ขอปุ่ม export หรือ API จาก HotelTime** | ยังไม่ได้ถาม | ✅ **ควรทำคู่ขนาน** — ราคาหนึ่งอีเมล ถ้าได้มาก็เลิกใช้ทางนี้ทั้งหมด |

### ตัดสินใจ: ทาง A — อ่านตาราง HTML

เหตุผล: ข้อมูลอยู่บนหน้าครบทั้ง 9 คอลัมน์อยู่แล้ว · โปรเจกต์นี้อ่าน DOM อยู่แล้วทุกที่ ·
ไม่ต้องพึ่งไลบรารีเพิ่ม · และ **ควบคุมความถูกต้องได้ดีกว่า PDF** เพราะเราเห็นค่าต่อเซลล์

พร้อมกับ **ส่งคำถามข้อ D ไปที่ HotelTime คู่ขนาน** — ถ้าเขามีปุ่ม export ที่ซ่อนอยู่ตาม role
หรือมี API ให้ เราทิ้งงานนี้ได้ทั้งก้อน ควรถามก่อนลงแรงเขียน

## 4. สิ่งที่ต้องแก้ในโค้ดเดิม

ใบนี้ **ไม่ใช่แค่เพิ่มไฟล์ใน `src/reports/`** เพราะมันหักสมมติฐานสองข้อของโครงปัจจุบัน

### 4.1 `Report` สมมติว่าทุกใบได้ไฟล์มา

ตอนนี้ `fetchChunk()` จบด้วย `downloadExport()` ที่คืนไฟล์ `.xlsx` เสมอ
ใบ Audit ไม่มีไฟล์ให้ดาวน์โหลด

**ข้อเสนอ:** เพิ่มฟิลด์แยกชนิดใน `Report`

```ts
extract:
  | { kind: 'download' }                          // สามใบเดิม — กดลิงก์ export
  | { kind: 'scrape'; gridSelector: string }      // ใบ Audit — อ่านตาราง
```

แล้วให้ `fetchChunk()` แตกทางตามชนิด · ฝั่ง scrape คืน `Sheet` (โครงเดียวกับที่ `xlsx.ts` คืน)
ทำให้ชั้นตรวจใช้ซ้ำได้ทั้งหมดโดยไม่ต้องแก้

### 4.2 `verifyChunk()` รับ path ของไฟล์ ไม่ใช่ข้อมูล

ตอนนี้เซ็นเจอร์คือ `verifyChunk(report, range, filePath, reportedRowCount)` แล้วมันเรียก
`readSheet(filePath)` ข้างใน

**ข้อเสนอ:** เปลี่ยนเป็นรับ `Sheet` ที่อ่านมาแล้ว — ผู้เรียกเป็นคนตัดสินว่าจะได้ `Sheet` มาจาก
ไฟล์หรือจาก DOM · เป็นการแก้เล็กและทำให้ `verify.ts` เป็น logic ล้วนสมบูรณ์ขึ้น

### 4.3 `DateRange` เป็นวันล้วน แต่ Audit ต้องการเวลา

`order.ts` เก็บวันที่เป็น UTC midnight และ `splitRange()` คืน `null` เมื่อเหลือวันเดียว
แต่ใบ Audit อาจต้องผ่าละเอียดกว่าวัน เพราะ filter รองรับ `HH:MM`

**ข้อเสนอ:** เพิ่ม `dayChunks()` คู่กับ `monthChunks()` และให้ `splitRange()` ผ่าลงไปถึงระดับ
ชั่วโมงได้เมื่อจำเป็น · **อย่าเปลี่ยน `monthChunks()` ที่ใช้อยู่** — สามใบเดิมทำงานถูกแล้ว

### 4.4 provenance ไม่มีไฟล์ให้ hash

`manifest.json` ตอนนี้เก็บ `sha256` ของไฟล์ `.xlsx` ที่ HotelTime ส่งมา

**ข้อเสนอ:** ฝั่ง scrape ให้บันทึก **HTML ดิบของตาราง** ลง `raw/<report>/<from>_<to>.html`
แล้ว hash ไฟล์นั้นแทน · รักษาคุณสมบัติ "ไบต์ที่ได้จากต้นทางโดยไม่ถูกแปลง" ไว้ได้เหมือนเดิม
และเปิดให้ตรวจย้อนหลังได้ว่าเราอ่านตารางถูกไหม

## 5. แผนการแบ่งก้อนที่เสนอ

**ก้อนละ 1 วัน** — วัดได้ 89 แถว/วัน (ก.ย. 2026) เทียบเพดาน 500 = เหลือระยะปลอดภัย 5.6 เท่า

⚠️ แต่ปี 2025 หนากว่านั้น (7 วันชนเพดาน = อย่างน้อย 71 แถว/วัน และอาจมากกว่ามาก)
**ต้องมีตัวผ่าครึ่งแบบปรับตัวเองเหมือนใบ `reservations-search`** โดยผ่าลงไปถึงระดับชั่วโมง

เกณฑ์ชนเพดาน: ได้ **500 แถวพอดี** → ถือว่าถูกตัด ผ่าครึ่งช่วงแล้วดึงใหม่

**ประมาณเวลา:** ~1.2 วินาที/ก้อน × ~860 วัน ≈ **17–20 นาที** สำหรับการดึงย้อนหลังทั้งหมด
ช้ากว่าสามใบเดิมมาก (92 วินาที) แต่ทำครั้งเดียว · รอบถัด ๆ ไปดึงแค่วันล่าสุดใช้เวลาไม่กี่วินาที

## 6. ชั้นตรวจที่ต้องปรับ

ห้าด่านเดิมใช้ได้เกือบหมด ที่ต้องเปลี่ยน:

| ด่าน | เปลี่ยนอะไร |
|---|---|
| เพดาน | `hasRowCap: true` แต่ค่าเพดานคือ **500** ไม่ใช่ 2,000 → ต้องทำให้ค่านี้ตั้งต่อรายงานได้ |
| จำนวนแถวจากหน้าเว็บ | หน้านี้**ไม่มีแถวสรุป** → `expectedRowCount()` คืน `null` |
| ช่วงวันที่ในไฟล์ | คอลัมน์ `Date` เป็น `DD/MM/YYYY HH:MM:SS` → `parseCellDate()` ยังไม่รองรับ ต้องเพิ่ม |
| ผลว่าง | ม.ค. 2024 ได้ 0 แถว → `hasResults()` ดูจำนวนแถวใน `#pc_dtgList` |

**ด่านใหม่ที่ควรมีเฉพาะใบนี้:** ยืนยันว่าแถวเรียงจากใหม่ไปเก่าจริง — ถ้าวันหนึ่งลำดับเปลี่ยน
สมมติฐานเรื่องทิศทางที่ข้อมูลหายจะผิดทันที และการผ่าครึ่งจะกู้ข้อมูลผิดส่วน

## 7. คำถามที่ต้องตอบก่อนเขียนโค้ด

1. **HotelTime มีปุ่ม export หรือ API ให้หน้านี้ไหม** — ถามก่อน ประหยัดงานทั้งก้อนได้
2. **ข้อมูล audit เริ่มวันไหนแน่** — อยู่ระหว่าง ม.ค. – พ.ค. 2024 ยังไม่ได้หาให้แน่
3. **HotelTime เก็บ audit ย้อนหลังนานแค่ไหน** — คำถามเดียวกับที่ค้างอยู่กับใบ Cancelled
   ที่มีข้อมูลแค่ 5 เดือน · ถ้า audit ก็ถูกล้างเป็นระยะ การดึงสม่ำเสมอจะสำคัญกว่าการดึงย้อนหลัง
4. **ต้องการทุก Operation หรือเฉพาะบางอย่าง** — มี 39 ชนิด รวมทั้ง `CHM synchronization`
   ที่ระบบยิงเองอัตโนมัติและกินสัดส่วนแถวเยอะ · ถ้าไม่ต้องการ การกรองออกจะลดปริมาณลงมาก
   และอาจทำให้ก้อนใหญ่ขึ้นได้
5. **สองคอลัมน์แรกที่ไม่มีหัวคืออะไร** — น่าจะเป็นไอคอนหรือปุ่มขยาย ถ้าเป็นปุ่มขยาย
   อาจมีรายละเอียดซ่อนอยู่ที่เรายังไม่เห็น
6. **ข้อมูลส่วนบุคคล** — audit trail มีชื่อผู้ใช้ระบบและอ้างอิงถึง reservation
   ต้องยืนยันว่าเก็บและส่งต่อได้ภายใต้เงื่อนไขเดียวกับรายงานอื่น
