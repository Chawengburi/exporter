# 08 · หลายเว็บ / หลาย instance

สถานะ: **DRAFT (2026-09-08)** — ยังไม่มีเว็บที่สองอยู่จริง ตัวเลขและกับดักในใบนี้จึงมาจาก
**การอ่านโค้ดที่มีอยู่** ไม่ใช่จากการสำรวจเว็บใหม่ · ส่วน §4 ทำได้ทันที ส่วน §5 **จงใจยังไม่ทำ**

คำถามต้นเรื่อง (เจ้าของ 2026-09-08): *"ในรูปแบบคล้าย ๆ นี้ มีวิธีใดบ้างที่ทำให้เป็น dynamic
เช่นหากนำไปใช้กับเว็บอื่นก็ export ได้"*

---

## 1. "dynamic" มีสามระดับ ราคาต่างกันคนละโลก

คำเดียวกันแต่หมายถึงงานสามขนาด · แยกให้ชัดก่อนตัดสินใจ ไม่งั้นจะจ่ายราคาระดับ 3
เพื่อแก้ปัญหาระดับ 1

| ระดับ | หมายถึง | ตัวอย่าง | สถานะวันนี้ |
|---|---|---|---|
| **1** | HotelTime เจ้าเดียวกัน คนละ instance / คนละโรงแรม | `th03.hoteltime.com`, โรงแรมที่สองบน `th07` | 🟡 ได้ 90% แล้ว ขาดแค่ profile |
| **2** | ซอฟต์แวร์คนละเจ้า แต่รู้ล่วงหน้าว่าเป็นเว็บไหน | hotelline, Opera, Cloudbeds | ⬜ ต้องมีชั้น `Site` |
| **3** | เว็บอะไรก็ได้ที่ยังไม่เคยเห็น | "ลูกค้าส่ง URL มา แล้ว export ให้เลย" | ⬜ ต้องจ่ายด้วย recon (§6) |

🔴 **ระดับ 3 ที่ทำโดย "ให้ agent ขับตอนรัน" ถูกตัดทิ้งแล้วใน spec 01** — และเหตุผลเดิม
แรงขึ้นเมื่อมีหลายเว็บ ไม่ใช่อ่อนลง · ดู §8

## 2. จุดผูกจริงในโค้ดวันนี้ — น้อยกว่าที่คิด และกระจุกอยู่ที่เดียว

สำรวจโค้ดทั้ง 2,172 บรรทัด (2026-09-08) แบ่งตามว่า "ย้ายไปเว็บอื่นได้เลยไหม"

| ชั้น | ไฟล์ | ผูกกับ HotelTime? |
|---|---|---|
| ตรรกะช่วงวันที่ / ซอยก้อน / รวมปี | `core/order.ts` | ❌ ไม่ผูก — ยกเว้น `ROW_CAP` และ `formatDMY` |
| ชั้นตรวจ | `core/verify.ts` | ❌ ไม่ผูก — รับ `Report` เข้ามาแล้วตรวจ |
| อ่าน xlsx | `core/xlsx.ts` | 🟡 ทน xlsx พิการของ HotelTime ได้ แต่ใช้ทั่วไปได้ |
| เขียน CSV | `core/csv.ts` | ❌ ไม่ผูก |
| กันความลับหลุด | `core/redact.ts` | ❌ ไม่ผูก |
| **คลิกเว็บ** | `core/webforms.ts` (276 บรรทัด) | 🔴 ASP.NET WebForms ทั้งไฟล์ |
| **ล็อกอิน** | `core/session.ts` | 🔴 role `Login`/`Password`/`Submit` |
| นิยามรายงาน | `reports/*.ts` (194 บรรทัด) | 🔴 แต่**เป็น plugin อยู่แล้ว** (spec 03) |

### จุดผูกที่ต้องย้ายเมื่อถึงเวลา — ทั้งหมดมีเท่านี้

| จุดผูก | ที่อยู่ | ทำไมมันผูก |
|---|---|---|
| `ROW_CAP = 2000` | `core/order.ts:18` | เพดานของ HotelTime · เว็บอื่นมีเลขของตัวเอง หรือไม่มีเลย |
| `EXPORT_LINK_NAME = 'Export: MS Excel'` | `core/webforms.ts:215` | ข้อความบนลิงก์ของ HotelTime |
| `isLoginPage()` regex `login\.aspx` | `core/webforms.ts:27` | นามสกุล `.aspx` คือ ASP.NET ล้วน |
| `/pms/` hardcode 4 ที่ | `commands/export.ts:122`, `:271`, `index.ts:73`, `config.ts:19` | prefix ของ HotelTime |
| `formatDMY()` = `DD/MM/YYYY` | `core/order.ts:42-49` | รูปแบบเดียวที่ช่องวันที่ของ HotelTime รับ |

⚠️ **`formatDMY` เป็นจุดผูกที่ซ่อนตัวดีที่สุด** — มันนั่งอยู่ในไฟล์ที่ดู "generic ที่สุด"
ของโปรเจกต์ แต่ผูกกับ locale ของเว็บต้นทางเต็มตัว · เว็บอเมริกาที่ใช้ `MM/DD/YYYY`
จะไม่ error ให้เห็น มันจะ **ยอมรับค่าแล้วกรองผิดเดือน** — `01/09/2026` อ่านได้ทั้งสองแบบ

### สิ่งที่ pipeline พิสูจน์แล้วว่าใช้ซ้ำได้

ลำดับใน [`../src/commands/export.ts`](../src/commands/export.ts) (`fetchChunk`, บรรทัด 107-110)

```
ซอยช่วง → ตั้ง filter → Search → ตรวจว่าฟอร์มไม่ถูกปฏิเสธ → ตรวจว่ามีผล
        → export → ตรวจไฟล์ → ผ่าครึ่งถ้าชนเพดาน → รวมเป็นไฟล์รายปี
```

**นี่คือสินทรัพย์จริงของโปรเจกต์ ไม่ใช่ selector** · ลำดับนี้ใช้ได้กับ portal ทุกใบที่มี
"ฟอร์ม filter + ปุ่มค้น + ปุ่ม export" ส่วนที่เขียนใหม่ทุกเว็บคือ DOM plumbing ~300 บรรทัด

## 3. ตัดสินใจ

| ระดับ | ตัดสิน | เหตุผล |
|---|---|---|
| 1 | ✅ **ทำ** — `--profile` (§4) | เกือบฟรี · แก้ปัญหาที่มีจริง (โรงแรมที่สอง) |
| — | ✅ **ทำเลย** — รวมจุดผูก 5 จุดจาก §2 ไว้ที่เดียว (§4.3) | ทำวันนี้ = ไม่ต้องรื้อวันหน้า |
| 2 | ⏸ **เลื่อน** จนมีเว็บที่สองอยู่จริง (§5) | abstraction ที่ออกแบบจากตัวอย่างเดียวผิดเสมอ |
| 3 | ⏸ **เลื่อน** — แต่เขียนทิศทางไว้ (§6) | ยังไม่มีความต้องการจริง |

🔑 **หลักที่ใช้ตัดสิน:** แยก "ทำให้ย้ายง่าย" (ทำตอนนี้ ถูก) ออกจาก "ทำให้ย้ายได้จริง"
(ทำตอนมีของจริง แพง) · การรวมค่าคงที่ไว้ที่เดียวไม่ใช่ abstraction มันคือการเก็บบ้าน
ส่วน `Site` interface คือ abstraction — และเรายังไม่มีข้อมูลพอจะออกแบบให้ถูก

## 4. ระดับ 1 — `--profile` (ทำได้ทันที)

### 4.1 ปัญหาที่มีตอนนี้

`PMS_BASE_URL` เป็น env อยู่แล้ว ([`config.ts:74`](../src/core/config.ts)) ตั้งเป็น shard อื่น
แล้ววิ่งได้เลย · แต่**จัดหลายที่พร้อมกันไม่ได้** เพราะ

- `.env` มีใบเดียว → สลับโรงแรมต้องแก้ไฟล์ทุกครั้ง
- `downloadDir` ล็อกที่ `PROJECT_ROOT/downloads` ตายตัว ([`config.ts:85`](../src/core/config.ts))
  → ไฟล์ของสองโรงแรมจะทับกัน **โดยที่ชั้นตรวจจับไม่ได้** เพราะชื่อไฟล์อ้างช่วงวันที่
  ไม่ได้อ้างที่มา

🔴 ข้อที่สองเป็นบั๊กเงียบคลาสเดียวกับที่ชั้นตรวจมีไว้ป้องกัน — ไฟล์ที่ "ดูปกติแต่ผิด"

### 4.2 สเปก

```
pms-export export --profile chaweng --report all
pms-export export --profile <name>   # ไม่ส่ง = ใช้ .env เดิม พฤติกรรมไม่เปลี่ยน
```

| เรื่อง | สเปก |
|---|---|
| ที่อยู่ไฟล์ตั้งค่า | `profiles/<name>.env` (gitignore ทั้งโฟลเดอร์ ยกเว้น `.gitkeep`) |
| ลำดับความสำคัญ | shell env > `profiles/<name>.env` > `.env` > default ในโค้ด |
| ที่อยู่ผลลัพธ์ | `downloads/<profile>/` · ไม่ส่ง `--profile` → `downloads/` เหมือนเดิม |
| `manifest.json` | เพิ่มฟิลด์ `profile` และ `baseUrl` |
| ไม่มีไฟล์ profile นั้น | `ConfigError` พร้อมรายชื่อ profile ที่มี — ไม่ fallback เงียบ ๆ |

🔴 **`manifest.json` ต้องบันทึก `baseUrl` ไม่ใช่แค่ชื่อ profile** — ชื่อ profile เป็นของเรา
เปลี่ยนได้ทุกเมื่อ ส่วน `baseUrl` คือหลักฐานว่าไบต์ชุดนี้มาจากไหนจริง · เหตุผลเดียวกับที่
spec 05 เก็บ `sha256` ไม่ใช่แค่ชื่อไฟล์

### 4.3 เก็บบ้านที่ทำพร้อมกัน

ย้ายค่าคงที่ทั้ง 5 จาก §2 มารวมที่ `core/config.ts` เป็นก้อนชื่อ `SITE` ก้อนเดียว

```ts
// core/config.ts — ก้อนนี้คือ "ทุกอย่างที่รู้ว่าเราคุยกับ HotelTime"
export const SITE = {
  id: 'hoteltime',
  appPrefix: '/pms/',
  loginUrlPattern: /login\.aspx/i,
  exportLinkName: 'Export: MS Excel',
  rowCap: 2000,
  dateFormat: 'DD/MM/YYYY',
} as const;
```

**ไม่ใช่ abstraction** — ยังเป็นค่าคงที่ตัวเดิม แค่มารวมที่เดียว · กำไรคือวันที่ทำ §5
งานจะเหลือแค่ "ทำ `SITE` ให้มีหลายก้อน" ไม่ใช่ตามล่า string ทั่วโปรเจกต์

⚠️ `dateFormat` ในก้อนนี้เป็น **ป้ายบอกความจริง ไม่ใช่สวิตช์** — `formatDMY()` ยังฮาร์ดโค้ด
รูปแบบเดียวอยู่ · ทำเป็นสวิตช์จริงเมื่อมีเว็บที่ใช้รูปแบบอื่นเท่านั้น จะได้เห็นของจริงก่อน

## 5. ระดับ 2 — ชั้น `Site` (ร่างไว้ **ยังไม่ทำ**)

ยกระดับสิ่งที่ทำกับ `Report` (spec 03) ขึ้นไปอีกหนึ่งชั้น

### 5.1 ร่างสัญญา

```ts
// sites/_types.ts
export type Site = {
  readonly id: string;                      // 'hoteltime' | 'hotelline'
  readonly rowCap: number | null;           // null = ไม่มีเพดาน
  isLoginPage(url: string): boolean;
  login(page: Page, creds: Credentials, redact: Redactor): Promise<LoginResult>;
  assertStillLoggedIn(page: Page): Promise<void>;
  reportUrl(report: Report): string;        // แทน /pms/ ที่ hardcode
  assertFormAccepted(page: Page): Promise<void>;
  downloadExport(page: Page, dest: string, timeoutMs: number): Promise<DownloadInfo>;
  readonly reports: readonly Report[];      // รายงานเป็นของ site
};
```

### 5.2 แผนย้ายไฟล์

| จาก | ไป |
|---|---|
| `core/webforms.ts` | `sites/hoteltime/webforms.ts` |
| `login()` ใน `core/session.ts` | `sites/hoteltime/login.ts` — `core/session.ts` เหลือแค่เปิด/ปิดเบราว์เซอร์ |
| `reports/*.ts` | `sites/hoteltime/reports/*.ts` |
| `ROW_CAP` ใน `core/order.ts` | `site.rowCap` — `verify.ts:75` รับมาเป็นพารามิเตอร์ |

`core/` เหลือแต่ของที่ไม่รู้จักเว็บใดเลย: `order`, `verify`, `csv`, `xlsx`, `redact`, `config`

### 5.3 🔴 เงื่อนไขที่ต้องเกิดก่อนจะเริ่มทำ

**อย่าเริ่มจนกว่าจะมีอย่างน้อยหนึ่งข้อ**

1. มีเว็บที่สองที่ตกลงแล้วว่าจะทำจริง **และสำรวจเสร็จแล้ว** (มี `recon/NOTES.md` ของมัน)
2. หรือมี HotelTime instance ที่โครงหน้าเว็บต่างจาก `th07` จริง ไม่ใช่แค่คนละ URL

เหตุผล: สัญญา `Report` ที่ใช้ได้ดีทุกวันนี้ **ออกแบบหลังสำรวจสามรายงานจริงเสร็จแล้ว**
ไม่ได้ออกแบบก่อน · ถ้าออกแบบ `Site` จากตัวอย่างเดียวจะได้ interface ที่เป็นรูปร่างของ
HotelTime แบบเปลี่ยนชื่อ แล้วเว็บที่สองจะไม่พอดี — เสียแรงสองรอบ

### 5.4 หลักฐานว่าชั้นนี้จะต้องยืดหยุ่นกว่าที่คิด

[spec 07](./07-spec-audit-trail-export.md) เจอหน้าที่ **ไม่มีปุ่ม export เลย** — อยู่บนเว็บ
*เดียวกัน* ด้วยซ้ำ · แปลว่าขั้น "ได้ไฟล์มา" มีอย่างน้อยสองแบบตั้งแต่ยังไม่ข้ามเว็บ:
โหลดไฟล์ กับ ขูดตารางเอง · `Site.downloadExport()` ในร่าง §5.1 จึงยังแคบเกินไป —
ของจริงต้องเป็น "ทำให้ได้ `Sheet` มา" ไม่ใช่ "กดลิงก์ดาวน์โหลด"

## 6. ระดับ 3 — จ่ายด้วย recon ไม่ใช่จ่ายด้วย runtime

spec 01 เลือก **"AI เขียน สคริปต์รัน"** (ใช้จังหวะ 1 กับ 3 ข้ามจังหวะ 2) · ทางที่สอดคล้อง
กับการตัดสินใจนั้นคือทำให้ **จังหวะที่ 1 ถูกลง** ไม่ใช่เปิดจังหวะที่ 2

```
pms-export recon <url>
```

เปิดเบราว์เซอร์ headful, ให้คนล็อกอินเอง, แล้วเก็บลง `recon/<site>/`: aria snapshot ทุกหน้าที่แวะ ·
ชื่อ control ทุกตัวในฟอร์ม · network log ตอนกด export · ตัวอย่างไฟล์ที่ได้ · ค่า default
ของช่องวันที่ทุกช่อง

แล้ว Claude เขียน `sites/<x>/` จากกองนั้น — **ต้นทุนเว็บใหม่ = recon session ครั้งเดียว**
ไม่ใช่จ่าย token ทุกคืน และไม่ใช่เขียนโปรเจกต์ใหม่

ข้อดีที่ไม่ตั้งใจแต่ได้มา: `recon` ใช้ได้กับ HotelTime เองตอนหน้าเว็บเปลี่ยน — ตรงกับ
"จังหวะที่ 3 · ซ่อมเมื่อพัง" ที่ spec 01 บอกว่ายังไม่ทำ

## 7. ทางสายกลางของ "declarative" ที่ยอมรับได้

spec 03 ปฏิเสธ JSON config ไว้แล้วและยังยืนอยู่ · แต่มีรูปแบบที่ได้ความสั้นโดยไม่เสีย type

```ts
// รายงานปกติ ~10 บรรทัด
export const someReport = defineReport({
  id: 'x', path: 'reports/X.aspx',
  dateFilter: { group: 'ctl00$pc$calCreated' },   // → applyFilters ให้เอง
  resultGrid: '#pc_dtgData',                      // → hasResults ให้เอง
  searchButton: 'ctl00$pc$btnFind',
  dateColumn: 'Created', expectedColumns: [...],
});

// ใบที่มีกับดัก override ทับเป็น TS ได้เต็มที่
export const rateCode = defineReport({
  ...,
  async applyFilters(page, range) { /* Period เป็นฟิลด์บังคับ ห้ามล้าง */ },
});
```

- ค่าที่ *เหมือนกันทุกใบ* เขียนแบบประกาศ
- ค่าที่ *เฉพาะตัว* ยังเขียนโค้ดทับได้ — ไม่ต้องประดิษฐ์ภาษาครึ่งใบ
- คอมไพเลอร์ยังบังคับครบเหมือนเดิม

⏸ **ยังไม่ทำ** — สามรายงานที่มีอยู่ใช้ default ร่วมกันได้แค่บางส่วน จะได้ helper ที่เดา
default จากตัวอย่างน้อยเกินไป · ทำเมื่อมีรายงานใบที่ 5-6 แล้วเห็นว่าอะไรซ้ำจริง

## 8. จงใจไม่ทำ

| ไม่ทำ | เหตุผล |
|---|---|
| JSON/YAML config ล้วนต่อรายงาน | spec 03 · 3 รายงานในเว็บเดียวกันยังต่างกันทุกมิติ · ข้ามเว็บยิ่งหนัก |
| 🔴 ให้ agent ขับเบราว์เซอร์ตอนรัน (จังหวะ 2) | spec 01 · agent ที่หลงทางจะ "หาทางอื่นจนสำเร็จ" แล้วส่งไฟล์ที่ดูสมเหตุสมผลแต่ผิดเข้าคลังเงียบ ๆ — ความเสี่ยงอันดับ 1 ของทั้งงาน และหลายเว็บ = หลายทางให้หลง |
| auto-detect ว่าเว็บนี้คือ site ไหน | เดาผิดแล้วได้ข้อมูลผิดเงียบ ๆ · ให้คนระบุ `--profile` / `--site` ตรง ๆ |
| ชั้นตรวจแบบ "generic ผ่านหมด" | §9 — เท่ากับทิ้งด่านเดียวที่จับได้ว่า filter ไม่ทำงาน |
| `storageState` / persistent profile ข้าม site | spec 06 · เหตุผลเดิม (session ฝั่ง server หมดอายุเอง) ไม่เปลี่ยน |

## 9. กับดักที่ต้องรู้ก่อนเพิ่มเว็บใด ๆ

### 9.1 🔴 ชั้นตรวจ generic ไม่ได้ — และมันคือหัวใจของเครื่องมือนี้

`verify.ts` เอง generic แล้ว แต่**ค่าที่มันใช้ตรวจ** ต้องสำรวจใหม่ทุกเว็บทุกรายงาน:
`dateColumn` · `hasRowCap` · `boundaryToleranceDays` · `expectedRowCount()` · `expectedColumns`

ถ้าเพิ่มเว็บใหม่แล้วใส่ค่าพวกนี้แบบ "ให้ผ่านไปก่อน" = ได้ dynamic มาโดยแลกกับสิ่งเดียว
ที่ทำให้เครื่องมือนี้เชื่อถือได้ · ค่าที่เชื่อไม่ได้ให้คืน `null` ให้ด่านนั้นถูกข้าม
**อย่าเดา** (spec 03) — และเขียนใน `recon/NOTES.md` ว่าทำไมเชื่อไม่ได้

### 9.2 เช็คก่อนว่าต้องใช้เบราว์เซอร์ไหม

ก่อนเขียน adapter ให้เว็บใหม่ ให้ดู network tab ก่อนเสมอ · เว็บอื่นอาจมี endpoint ที่ replay
ด้วย cookie ได้ตรง ๆ — ตอนสำรวจ uploader เจอว่าครึ่งขาอัปโหลด **ไม่ต้องใช้ browser เลย**
(2026-09-03) · HotelTime ทำไม่ได้เพราะ `__VIEWSTATE` แต่นั่นเป็นข้อจำกัดของ WebForms
ไม่ใช่ของทุกเว็บ · adapter ที่เป็น HTTP ล้วนเร็วกว่าและพังน้อยกว่า Playwright หลายเท่า

### 9.3 anti-bot / 2FA คือตัวเปลี่ยนเกม ไม่ใช่รายละเอียด

HotelTime ไม่มีทั้งคู่ (วัดจริง spec 02) ซึ่งเป็นเหตุผลที่ทั้งโปรเจกต์นี้ถูกและง่าย ·
เว็บใหม่ที่มี 2FA จะทำให้ "ล็อกอินใหม่ทุกรอบ" (spec 06) ใช้ไม่ได้ทันที และเป็นคนละโจทย์
ไม่ใช่ adapter อีกใบ · **ตรวจข้อนี้ก่อนสัญญาอะไรกับใคร**

### 9.4 credential ต้องแยกต่อ site ไม่ใช่ต่อโปรเจกต์

`PMS_USERNAME`/`PMS_PASSWORD` เป็น env ระดับโปรเจกต์ ([`config.ts:94`](../src/core/config.ts))
· หลาย site = หลายชุดรหัส · `--profile` (§4) แก้ข้อนี้ให้แล้ว แต่ `redact.ts` ต้องได้รหัส
**ของ profile ที่กำลังใช้** ไปปิดบัง ไม่ใช่ของ `.env`

### 9.5 เพดานแถวต้องวัด ไม่ใช่คัดลอก

`ROW_CAP = 2000` วัดมาจาก `ReservationListMaster` ใบเดียว · ใบ RateCode ในเว็บเดียวกัน
ไม่มีเพดาน · หน้า Audit trail เพดาน 500 (spec 07) · **เว็บใหม่ต้องวัดเอง** ตามขั้นที่ 2
ของ "วิธีเพิ่มรายงานใหม่" ใน spec 03

## 10. สรุปสำหรับคนที่มารับงานต่อ

- **อยากรองรับโรงแรม/shard ที่สอง** → §4 · ครึ่งวัน · ทำได้เลย
- **อยากรองรับ PMS คนละเจ้า** → §5 แต่ **ไปสำรวจเว็บนั้นก่อน** อย่าเริ่มด้วยการรีแฟกเตอร์
- **อยากให้ "ใส่ URL อะไรก็ได้"** → §6 · และอ่าน §8 ให้จบก่อน
- **จะแตะโค้ดวันนี้เลย** → ทำแค่ §4.3 (รวมค่าคงที่) ก็ได้กำไรมากที่สุดต่อความเสี่ยงต่ำสุด
