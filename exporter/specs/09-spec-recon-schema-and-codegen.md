ดู **§15** ท้ายไฟล์ — คำตัดสินคือ **GO ทำ §12 ก่อน (ฟรี ไม่มีความเสี่ยง) / ยังไม่ GO เขียน

> *"หากไม่มีการจ้างงานแล้ว และฉันไม่ได้มาสั่ง claude ให้ใช้ playwright ไปสำรวจหรือเขียน script
> แล้ว และมี data ใหม่ที่ user ต้องการจะ export ออกมาจะทำอย่างไรให้ง่ายและ automate ·

## 1. เปลี่ยนหน่วยวัดก่อน — resource ที่หายากคือ token ไม่ใช่เวลา dev

spec 01-08 ทุกใบคิดต้นทุนเป็น *เวลา developer* ("ครึ่งวัน") · **หน่วยนั้นผิดสำหรับโจทย์นี้**

ในสถานการณ์ที่เจ้าของอธิบาย ไม่มี developer ให้จ้าง มีแต่ **โควตา token ของเจ้าของเอง**
และมันหมดเร็วกว่าที่ควรมาก · ทุกการตัดสินใจในใบนี้จึงวัดด้วยหน่วยเดียว:

> **กี่ token ต่อรายงานใหม่หนึ่งใบ**

## 2. token หมดไปกับอะไร — ไม่ใช่การเขียนโค้ด

ประมาณจากขนาดไฟล์จริงใน `recon/captures/` (สำรวจ 2026-09-08, ~4 ไบต์ต่อ token)

| ไฟล์ | ขนาด | ≈ token |
|---|---|---|
| `audit-aria.yml` | 117.8K | ~30,000 |
| `res-search-by-results-aria.yml` | 70.2K | ~18,000 |
| `res-cancelled-results-aria.yml` | 36.6K | ~9,000 |
| `res-search-by-aria.yml` | 13.0K | ~3,000 |
| อีก 4 ไฟล์ | ~22K | ~6,000 |
| **รวม snapshot ที่ต้องเข้า context** | **~250K** | **~65,000** |

และนั่นคือการ "มองหน้าเว็บ" **รอบเดียว** · ของจริงต้องมองซ้ำหลายรอบ (กด Search แล้วดูใหม่,
ล้างช่องวันที่แล้วดูใหม่, ลองผิด) → **หลักแสน token ต่อเว็บ**

เทียบกับผลผลิตปลายทาง:

| ผลผลิต | ขนาด | ≈ token |
|---|---|---|
| `src/reports/*.ts` ทั้ง 3 ใบรวมกัน | 194 บรรทัด (11.1K) | ~3,000 |

> 🔑 **~97% ของ token หมดไปกับ "มองหน้าเว็บ" ไม่ใช่ "เขียนโค้ด"**

**ข้อสรุปที่ตามมา:** การลด token ไม่ได้อยู่ที่เขียนโค้ดให้สั้นลง หรือใช้โมเดลถูกลง แต่อยู่ที่
**เอาการมองหน้าเว็บออกจาก context ของเจ้าของ**

## 4. recon schema — หัวใจของทั้งใบ

ปัญหาของ recon วันนี้: มันคืนมาเป็น *หน้าเว็บทั้งหน้า* ให้ Claude ตีความ
สิ่งที่ต้องการจริง ๆ มีแค่ไม่กี่สิบค่า

```jsonc
// recon/schema/report.schema.json — ฟอร์มใบเดียว ใช้กับทุกเว็บทุกรายงาน
{
  "site":   { "id", "baseUrl", "appPrefix", "loginUrlPattern" },
  "login":  { "url", "userField", "passField", "submitSelector", "has2FA" },

  "report": {
    "id", "label", "path",
    "isPlainGet": false          // 🔑 §10 — ถ้า true แทบไม่ต้องใช้ Playwright เลย
  },

  "dateFilter": {
    "targetGroup",               // เช่น "ctl00$pc$calIssued"
    "format",                    // "DD/MM/YYYY" — ต้องบันทึกที่ *สังเกตเห็น* ไม่ใช่ที่เดา
    "mustClearGroups": []        // 🔴 ช่องที่ถูก prefill ไว้และต้องล้างก่อน
  },

  "searchButton", "resultGrid",
  "exportLink":  { "text", "selector", "downloadUrlPattern" },

  "fileShape":   { "sheets", "tablesPerSheet", "headerRowIndex", "columns": [] },
  "totalsRow":   { "label", "matchesFileRowCount": true|false|null },
  "rowCapProbe": { "observed": null }   // null = ยังไม่ได้วัด — ห้ามเดา
}
```

### 4.1 🔴 ฟิลด์ที่ต้องยอมให้เป็น `null` ได้ทุกฟิลด์

`null` = **"ยังไม่รู้"** ไม่ใช่ "ไม่มี" · ตาม [spec 03](./03-spec-report-definition.md) — ค่าที่เชื่อไม่ได้
ให้คืน `null` เพื่อให้ด่านนั้นถูกข้าม **อย่าเดา**

generator ต้องแปล `null` เป็นโค้ดที่ *ข้ามด่านนั้นพร้อมคอมเมนต์บอกเหตุผล* ไม่ใช่เติมค่ามั่ว ๆ
ให้ผ่าน · ค่าที่เดามาแล้วดูสมเหตุสมผลอันตรายกว่าค่าที่ว่าง เพราะมันปิดปากชั้นตรวจ

### 4.2 หลักฐานว่าฟอร์มนี้ต้องมี `mustClearGroups`

ไม่ใช่ฟิลด์ที่คิดขึ้นเอง — มาจากกับดักจริงใน
[`src/reports/reservations-search.ts`](../src/reports/reservations-search.ts):
`calArrival` ถูก prefill เป็น "วันนี้ → อีก 1 ปี" ตั้งแต่เปิดหน้า ถ้าไม่ล้างก่อน
ผลจะเป็น intersection ที่ผิด **โดยไฟล์หน้าตาปกติทุกประการ**

**กับดักชนิดนี้คือเหตุผลที่ recon schema ต้องมีอยู่** — ถ้าไม่มีช่องให้กรอก คนสำรวจ
(หรือ agent) จะไม่รู้ด้วยซ้ำว่าต้องมองหา

## 5. สามวิธีเติมฟอร์ม — เรียงตามราคาที่เจ้าของจ่ายจริง

### 5.1 🥇 `pms-export recon <url>` — คนขับ (ทำก่อน)

```bash
pms-export recon https://th07.hoteltime.com/pms/reports/housekeeping/Cleaning.aspx
```

เปิด headful → **คนคลิกไปหน้าที่ต้องการเอง กรอก filter เอง กด Search เอง กด Export เอง**
→ สคริปต์ capture เงียบ ๆ ทั้ง session: HTML ทุกหน้า, ชื่อ control ทุกตัว, network log
ตอนกด export, ไฟล์ที่ได้ → กรอก `recon/<site>/<report>.json` ให้อัตโนมัติเท่าที่ parse ได้
แล้วเหลือ `null` ไว้ให้คนเติม

| | |
|---|---|
| **token** | **0** |
| **เงิน** | **0** |
| เวลาคน | ~2 นาที |

🔑 **คนคลิก 5 ครั้ง แทนที่จะให้ AI งม 30 step** · และคนที่คลิกไม่จำเป็นต้องเป็น developer —
เป็น user ที่รู้ว่าตัวเองอยากได้รายงานไหนก็พอ ซึ่ง**ตอบโจทย์ต้นเรื่องตรงที่สุด**

### 5.2 🥈 TinyFish — เมื่อไม่มีคนขับ

```bash
tinyfish agent run "ล็อกอิน ไปหน้ารายงาน X แล้วกรอกฟอร์มตาม schema" \
  --url <url> --use-profile \
  --output-schema-file recon/schema/report.schema.json \
  --capture-html --sync > recon/<site>/<report>.json
```

การเดินหน้าเว็บเกิดบนคลาวด์ TinyFish — **ไม่เข้า context เจ้าของเลยสักไบต์** กลับมาเป็น JSON ~2KB

| | |
|---|---|
| **token** | **~2,000** (แค่อ่านฟอร์มที่กรอกแล้ว) |
| **เงิน** | ~$0.3-0.5 (`$0.016`/step) |

ล็อกอินได้โดยไม่ต้องส่งรหัส: `tinyfish profile import-cookies --domain <site>`
ดูด cookie จาก Chrome เครื่องนี้ขึ้นไปเป็น Browser Context Profile

🔴 **ทดสอบแล้ว 2026-09-14 — ทางนี้ยังใช้กับ HotelTime ไม่ได้**

`import-cookies` รายงาน `Cookies uploaded: 1` แต่ cookie ที่ HotelTime ใช้ยืนยันตัวตน
มี 2 ใบและ**ทั้งคู่เป็นชนิด session** (`expires_utc = 0`) ซึ่งตัวนำเข้าข้าม ·
ที่ขึ้นไปได้ใบเดียวคือ `...forms.usrsHistData` ซึ่งเป็นแค่ประวัติการใช้งาน

ยิงจริง 2 รอบ 2 profile (9 ขั้นรวม ≈ $0.14) → agent ตอบว่า
`หน้าจอแสดงเป็นหน้า login` ทั้งคู่ · หลักฐานดิบที่ [`../demo/evidence/`](../demo/evidence/)

⚠️ **กับดักเพิ่ม 2 ข้อ** (ตรวจผ่าน `/v1/profiles/<id>` — CLI ไม่มีคำสั่ง list)

1. `import-cookies` ที่ไม่ระบุ `--profile-id` สร้าง profile ใหม่ **แต่ไม่ตั้งเป็น default**
   ส่วน `--use-profile` เฉย ๆ หยิบใบ default ซึ่ง **มี 0 cookie** → agent โผล่หน้า login
   โดยไม่มีอะไรบอกว่าใช้ผิดใบ
2. `import-cookies` **สร้าง profile ใหม่ทุกครั้งที่รัน โดยใช้ชื่อเดิม** — แยกด้วยตาไม่ได้
   และทำให้ id ที่ปักหมุดไว้ในสคริปต์เก่าทันที

→ **อย่าปักหมุด id** · resolve ใบใหม่สุดที่ชื่อตรงตอนรัน (ดู `demo/resolve-profile.mjs`)
หรือระบุ `--profile-id` ตอน import เพื่อเขียนทับใบเดิม

ทดสอบซ้ำหลังล็อกอิน Chrome ใหม่สด ๆ (07:54) — ยังได้ `cookie_count: 1` เท่าเดิม
**ยืนยันว่าไม่ใช่ปัญหา session หมดอายุ**

**นัยต่อสเปกใบนี้:** §5.2 ใช้ได้กับเว็บที่ไม่ต้องล็อกอิน หรือเว็บที่ใช้ cookie

ที่ใช้ session cookie** ต้องยอมมอบรหัสผ่านให้ TinyFish ซึ่งขัดกับเหตุผลที่เลือกทางนี้

## 7. generator

```
recon/<site>/<report>.json  →  generate  →  src/reports/<id>.ts  (+ diff ให้คนดู)
```

- ผลลัพธ์เป็น **TypeScript ที่อ่านออกและแก้ต่อด้วยมือได้** ไม่ใช่ config ที่ runtime ตีความ —

  แก้ด้วยมือทับได้เลย ไม่ต้องกลับไปแก้ recon json
- ทุกฟิลด์ที่เป็น `null` → คอมเมนต์ `// ⚠️ ยังไม่ได้วัด: <ฟิลด์> — ด่าน <x> ถูกข้าม`
- ต่อยอดจาก `defineReport()` ใน [spec 08 §7](./08-spec-multi-site.md) ได้ตรง ๆ

## 8. ชั้นตรวจที่ scale ไปถึง ~40 ชนิดข้อมูลได้

เจ้าของแจ้ง 2026-09-10 ว่าข้อมูลมี **~40 ประเภท** (ตัวเลขประมาณ — ดู §0: ของจริงที่วัดได้
2026-09-18 คือ **66 หน้าที่มีปุ่ม export** สูงกว่าที่ประมาณไว้ ~65%) · เขียน contract ด้วยมือ
40+ ใบไม่คุ้ม แยกเป็นสองกอง กองแรกเขียนครั้งเดียว กองที่สองไม่ต้องเขียนเลย

### 8.1 กฎจับ "โดนตัด" — 1 ใบ ใช้กับทุกชนิดทุกเว็บ

ทำงานได้ **โดยไม่ต้องรู้จักเว็บนั้นเลย** เพราะดักที่ *รูปร่างของการโดนตัด* ไม่ใช่ที่ตัวเลขเพดาน

| สัญญาณ | ทำไมไม่ต้องรู้จักเว็บ |
|---|---|
| ขอ 24 เดือน ได้ข้อมูลครอบคลุม 8 เดือน | เทียบ "ช่วงที่ขอ" กับ "ช่วงที่ได้" ได้เสมอ |
| **จำนวนแถวเป็นเลขกลมเป๊ะ** (500 / 1000 / 2000 / 5000) | เพดานระบบมักเป็นเลขกลม ข้อมูลจริงไม่ค่อยเป็น |
| แถวสุดท้ายจบกลางเดือน ไม่ใช่ปลายช่วงที่ขอ | การตัดเรียงตามลำดับเสมอ |
| **ซอยช่วงครึ่งหนึ่งแล้วแถวรวม > เดิม** | ✅ พิสูจน์การโดนตัดได้ 100% ไม่ต้องเดา |
| รอบนี้ 40 แถว รอบที่แล้ว 4,000 | เทียบกับประวัติของตัวเอง |

🔑 **ข้อ 4 คือกลไกที่จับเพดาน 2000 ได้จริงเมื่อ 2026-09-08** (ดู `recon/NOTES.md`) — และมันเป็น
ตรรกะล้วน ไม่มีอะไรเกี่ยวกับ HotelTime · **เขียนครั้งเดียว ใช้ได้กับเว็บที่ยังไม่เคยเห็น**

### 8.2 รูปร่างข้อมูลของแต่ละชนิด — เรียนจาก export ครั้งแรก ไม่ต้องเขียน

ครั้งแรกที่ export ผ่านและ**คนยืนยันว่าถูก** → บันทึกเป็น baseline:
กี่ sheet, กี่ table ต่อ sheet, header อยู่แถวไหน, ชื่อคอลัมน์, ช่วงจำนวนแถวปกติต่อเดือน
→ ครั้งต่อไปเพี้ยนไปจากนี้ = เตือน

| | ต้นทุนการเขียน |
|---|---|
| กฎ §8.1 | เขียนครั้งเดียว |
| baseline 40 ชนิด | **0 — generate จากของจริง** คนแค่กดยืนยันครั้งเดียว |

⚠️ **ข้อจำกัดที่ต้องพูดให้ชัด:** baseline จับ "ผิดตั้งแต่วันแรก" ไม่ได้ มันจับได้แค่
*การเปลี่ยนแปลงจากวันแรก* · การยืนยันครั้งแรกจึงเป็นขั้นที่คนต้องดูจริง ไม่ใช่กดผ่าน

## 9. 🔴 ทำไมยังต้องโหลดไฟล์ที่เครื่องนี้ — เปลี่ยนไม่ได้

3. ไฟล์จริงมีหลาย sheet / หลาย table ซ้อนใน sheet เดียว (เจ้าของยืนยัน 2026-09-10) —

## 13. คำถามที่ยังเปิดอยู่

### 13.1 ผ่า xlsx ที่มีหลาย table ใน sheet เดียว

เจ้าของแจ้งว่ามีไฟล์แบบ "หลาย table ซ้อนใน sheet เดียว" และ "table เดียวแต่หลาย sheet"

**ข้อเสนอ: อย่าเอามาขวางท่อ export**

```
export     → ได้ไฟล์แท้ + พิสูจน์ว่าไม่โดนตัด → uploader    ← ใบนี้
normalize  → ผ่า multi-table เป็นตาราง        → warehouse   ← spec คนละใบ ทำทีหลัง
```

ชั้นตรวจต้องอ่านไฟล์บ้างเพื่อนับแถว/หาช่วงวันที่ แต่เป็นการ **อ่านตื้น** ("แต่ละ sheet
มีกี่แถว, ค่าที่หน้าตาเป็นวันที่ min/max เท่าไหร่") ซึ่งไม่ต้องเข้าใจโครงสร้าง 40 แบบ

### 13.2 คนที่กด `recon` เป็น user ไม่ใช่ developer — UI พอไหม

§5.1 ตั้งใจให้ user กดเองได้ แต่ยังต้องมีคนเติมฟิลด์ที่ parse ไม่ได้ (`rowCapProbe`,
`dateFilter.format`) · ยังไม่รู้ว่าเส้นแบ่งอยู่ตรงไหน — **ต้องลองกับ user จริงหนึ่งคนก่อน**

### 13.3 40 ชนิด ต้องรันบ่อยแค่ไหน

ยังไม่มีข้อมูล · ถ้าส่วนใหญ่รันครั้งเดียวแล้วเลิก การลงทุนสร้าง adapter อาจไม่คุ้ม
และควรอยู่ที่ lane ad-hoc แทน · **ถามเจ้าของก่อนขยายจาก 3 เป็น 40**

## 15. 🔑 คำตัดสิน go/no-go (แก้ไข 2026-09-18)

### จำนวนรายงานจริง ไม่ใช่ตัวเลขประมาณ

**66 หน้า** มีปุ่ม export จริง (วัดจาก `pms-export sweep`, `recon/menu-sweep.json`) — ทำไปแล้ว
3 ใบ เหลือ **63 ใบ** ที่ยังไม่มีนิยาม

### ต้นทุนวันนี้ ถ้าไม่เปลี่ยนอะไรเลย

recon เชิงลึกแบบ AI อ่านทั้งหน้า ~30,000–65,000 token/หน้า (§2) × 63 ใบ ≈ **1.9–4.1 ล้าน token**
เพื่อทำให้ครบ 66 ใบ — ยืนยันด้วยตัวเลขจริงว่าวิธีเดิมทำไม่ไหวสำหรับสเกลนี้ (ไม่ใช่แค่ทฤษฎี
อีกต่อไป เพราะตอนนี้รู้จำนวนใบจริงแล้ว)

### ต้นทุนที่ลดไปแล้วจริง (ไม่ใช่ที่วางแผนไว้)

`pms-export sweep` ทำงานที่เคยคิดว่าต้องเสีย token ไปแล้วสำหรับทั้ง 66 ใบพร้อมกันในการรัน
ครั้งเดียว **~8,150 token รวม** (ไม่ใช่ต่อใบ) — ได้ชื่อหน้า, มีปุ่ม export ไหม, ชื่อ control
ในฟอร์มเต็มรายการ, กลุ่มช่องวันที่ที่พบ (`$calFrom`/`$calTo`) ต่อทั้ง 66 ใบ ส่วนที่เหลือที่
sweep **ให้ไม่ได้** (ต้องมี recon เชิงลึกหรือคนดูจริง): ค่า default ที่ prefill ไว้ในแต่ละช่อง
(`mustClearGroups` ต้องรู้ว่าช่องไหน prefill มาแล้ว sweep วันนี้ยังไม่ได้อ่าน `value` ของ input,
เก็บแค่ `name`), ฟิลด์บังคับที่ห้ามล้าง, เพดานแถว, รูปร่างไฟล์ผลลัพธ์ (กี่ sheet, header แถวไหน)
— ทั้งหมดนี้ต้องลอง export จริงอย่างน้อยหนึ่งครั้งถึงจะรู้ ไม่มีทางลัดจาก sweep

### ขั้นที่ต้องผ่านก่อนลงแรงเต็มใบ (ตามที่ GO ไว้)

ลำดับเดียวกับที่ §12 วางไว้ตั้งแต่ต้น ยังไม่เปลี่ยน — สิ่งที่เพิ่มคือตอนนี้มีข้อมูลจาก sweep
มาช่วยกรอก schema ย้อนหลังได้เร็วขึ้น:

1. กรอก `report.schema.json` ย้อนหลังของ 3 รายงานที่มีอยู่ — ใช้ข้อมูลจาก
   `recon/menu-sweep.json` (ชื่อ control, กลุ่มวันที่) เป็นจุดตั้งต้น แล้วเติมส่วนที่ sweep
   ให้ไม่ได้ด้วยมือจากความรู้ที่มีอยู่แล้วใน `src/reports/*.ts`
2. เขียน generator ต้นแบบ (ยังไม่ต้อง production-grade) แปล schema → เทียบกับ
   `src/reports/*.ts` ที่เขียนมือ
3. อ่านผลตามตารางใน §12 เดิม (ใกล้เคียงทั้ง 3 / 2 ใบ / แก้มือแทบทั้งหมด) — **ยังไม่มีใครทำข้อนี้**
   นี่คือสิ่งเดียวที่ยืนคาอยู่ระหว่างใบนี้กับการตัดสินใจจริง
